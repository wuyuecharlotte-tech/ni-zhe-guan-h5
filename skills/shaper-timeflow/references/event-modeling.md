# 业务事件建模与接入

本文件描述通用事件建模原则。平台不解释业务事件的定义、payload、时间语义或消费者；
接入方负责项目级事件契约。仅当业务需要可靠事实记录时才登记事件。

## 1. 边界与候选判断

| 通道 | 表达 |
|---|---|
| `windows` | 区间内的速率或容量修正 |
| `points` | 点时刻的值变化或 phase 推进 |
| `business-events` | 已成功发生的不可变业务事实 |

效果记录不等于事实记录。一个动作可以同时产生效果记录和事实记录。
`business-events` 不替代窗口或点事件，也不进入结算输入。

业务事件登记是可选项。开发者在动作成功后依次判断：

1. 是否为已成功发生、值得回溯的动作或业务决定？
2. 当前 projection、结算报告或业务快照能否可靠还原该事实？
3. 是否存在审计、历史、统计、任务进度、通知、客服追溯或下游消费需求？
4. 是否有稳定的 `eventId` 和已声明的 `kind`？

有明确历史还原或消费需求时可登记；已有权威记录完整覆盖、事实可由当前状态可靠
还原，或仅属于派生状态时可以不登记。平台只要求激活定义的 `events[]`
声明 `kind`。

## 2. 项目侧事件契约

激活定义中的 `events[]` 只提供 `kind` 和展示信息，不是完整业务契约。每个事件
类型应由项目侧定义：

| 契约项 | 要求 |
|---|---|
| `kind` | 稳定类型标识，不复用不同事实 |
| 所有者 | 负责定义和演进的生产方 |
| 语义 | 精确表示一个已发生事实 |
| payload schema | 必填、可选字段、类型、约束和未知字段策略 |
| `schemaVersion` | payload 结构版本与升级规则 |
| 时间语义 | `eventTime` 表示哪个业务时刻 |
| 对象引用 | scope、stream、业务对象和动作的关联方式 |
| `eventId` | 分配方式、重试规则和唯一范围 |
| 消费者 | 审计、统计、任务、通知或下游系统 |
| 生命周期 | 发布、弃用、保留和访问控制 |

平台不校验 payload 内容，因此 BFF 或项目服务必须在发送前校验 schema。新增可选
字段通常可保持主版本；字段语义、类型或必填性变化应升级版本。禁止用同一 `kind`
承载不同事实。

如果 payload 包含资源值，明确采用平台刻度还是显示刻度；两者不得混用，也不能
在没有换算说明的情况下与其他资源横向比较。

## 3. 时间与标识

平台仅要求 `eventTime` 为非负 Unix 毫秒。项目契约必须明确它表示请求、发生、
生效、完成或业务确认中的哪一个时刻；如需要多个时刻，应在 payload 中分别定义，
不要用一个时间字段承担多种含义。

平台对业务事件按 `(workspace_id, event_id)` 做幂等。`eventId` 不是全局唯一；
项目可进一步规定禁止跨 scope 复用。建议使用独立标识：

- `actionId`：一次业务动作及效果、事实的关联键；
- `correlationId`：跨多个动作的业务链路；
- `causationId`：直接触发当前事实的上游事件；
- `eventId`：当前事实的类型化幂等键。

重试必须复用同一 `eventId` 和相同 payload；同键同载荷重放，同键不同载荷冲突。

## 4. 可靠性与部分成功

可靠性应与事实重要性匹配，不要为所有动作强制引入 outbox：

| 重要性 | 建议 |
|---|---|
| 无消费需求 | 可不登记 |
| 辅助审计 | 直接登记并记录失败 |
| 事实必须可恢复 | 本地事务 + outbox + 重试 |
| 实时下游消费 | 单独的 BFF 消息机制或现有 delivery，不依赖 business-events |

关键事件的通用顺序：

```text
校验与幂等预留
  -> 应用窗口、点事件或业务状态效果
  -> 本地事务写业务结果和 outbox
  -> worker 登记 business-events
  -> 成功后标记事实已登记
```

说明各类部分成功：

- 效果失败：不报告动作成功，不登记事实。
- 效果成功、本地事务失败：通过 `actionId` 对账或补偿。
- 本地成功、事件未登记：由 outbox 重试。
- 事实已登记、本地状态未知：通过 `eventId` 和 `actionId` 对账，不重复创建事实。
- 网络超时：保留原幂等键并重试或查询，不直接认定成功或失败。

outbox 状态和实现属于项目侧，至少应区分待发送、发送中、已接受、可重试失败和
需要人工处理。事件登记失败不得回滚已成功的平台效果，但必须留下可见的重试状态。

## 5. 消费者与投递

`business-events` 是事实登记，不是订阅或实时投递协议。需要实时消费时，应由 BFF
明确使用消息系统或现有的 `change_event`/`change_delivery`，并说明业务事实与
结算变化事实的区别。

下游应用应使用稳定的 `deliveryId` 或项目侧幂等键。不得把事件摘要直接当作下游
应用摘要，也不得把未确认的下游处理报告为成功。

## 6. 生命周期、隐私与观测

项目应定义事件类型的发布、版本、弃用、历史保留和消费者兼容规则。payload 不应
包含不必要的身份、凭据、精确位置或敏感业务信息；日志和错误不得回显完整 payload。

至少观测：

- 事件登记成功率和失败率；
- 重试积压、延迟和需要人工处理的数量；
- schema 校验失败；
- 效果成功但事实长期未登记的对账差异；
- 消费者确认与投递状态。

## 7. 验收

若选择登记事件，至少验证：

- `events[]` 已声明 `kind`；
- payload 符合项目 schema；
- `eventTime` 语义已在契约中定义；
- `eventId` 重试稳定，同键同载荷重放且同键不同载荷失败；
- 事件不改变流值、窗口或结算；
- 效果成功、事件失败时有可恢复状态；
- 关键事实覆盖 outbox 重试、部分成功和对账。

若选择不登记，应说明权威事实由哪里保存、为什么无需平台时间轴或下游消费。
