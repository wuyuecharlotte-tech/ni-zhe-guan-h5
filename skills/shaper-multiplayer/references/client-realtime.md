# 客户端实时体验（预测、和解与插值）

本文件是实时竞技类游戏中**客户端侧实时表现**的权威落点：本地预测、回滚与重放、服务端和解、输入缓冲与序号、插值与外推，以及网络状态可视化。它只回答一个问题——客户端在**不违反服务端权威**的前提下，如何让画面跟手且不抖。

两条不变量先写在最前面，后文所有做法都不得与之冲突：

1. **预测与插值都不产生权威状态。** 预测结果只存在于本地表现层，绝不写回权威状态，也绝不作为命令 payload 回传给服务端。
2. **断线不重放输入。** 断线期间不排队、不回放本地输入，预测缓冲在断线时丢弃；重连后以服务端权威快照重建。这条与 [断线与刷新重连](reconnection.md) §2、§5 完全一致。

## 适用范围

- **适用**：移动、瞄准、射击、物理推进等高频输入，客户端必须在服务端确认前就给出反馈的实时竞技场景。首选 recipe 是 [`examples/realtime-arena`](../examples/realtime-arena/README.md)。
- **通常不适用**：回合制、棋盘、卡牌、派对等低频决策场景——它们在收到服务端结果前不推进本地模拟，预测只带来复杂度，没有回报。判据见文末「什么时候不需要预测」。

本文件只覆盖客户端侧，与既有权威的分工如下。任何主题的操作细节以对应的权威文件为准，本文不重复：

| 主题 | 权威文件 |
| --- | --- |
| 状态归属、时间与随机性的归属 | [架构与归属](architecture.md) |
| 服务端固定 tick、输入最多消费一次 | [玩法模式](gameplay-patterns.md) |
| 断线、宽限期、刷新重连（不排队、不重放） | [断线与刷新重连](reconnection.md) |

## 数据流

```text
输入产生
  -> 打上本地序号 sequence
  -> 进入本地预测缓冲（仅表现层）
  -> sendInput("input", { sequence, ... })   // 可丢弃；返回 false 即丢
  -> 本地预测推进渲染状态

收到权威状态（服务端 tick 投影）
  -> 以权威快照为基准回滚本地预测状态
  -> 重放缓冲中 sequence > 已确认序号的输入
  -> 与预测位置比较：误差 < 阈值 -> 平滑收敛；>= 阈值 -> 硬切
  -> 渲染（滑动插值缓冲）
```

图里有三个必须分开存放的状态：**预测状态**、**权威快照**和**渲染状态**。它们永远不互相赋值。把预测状态当权威状态用，或把渲染状态回传给服务端，都会破坏服务端权威，也就是 [SKILL.md](../SKILL.md) 的不可协商边界。

## 输入序号与输入缓冲

客户端为每条输入打一个**单调递增的本地序号**（`sequence`），并把它随输入一起发送：

```ts
// 边界草图，需对照上游 v0.18.0 skill 与已发布 SDK 核实 API。
// 本地序号只在一次会话内单调递增；它不是权威时间，也不参与服务端结算。
let nextSequence = 0;
const pending: Array<{ sequence: number; input: Input }> = []; // 未确认输入（仅表现层）

function capture(input: Input): void {
  const sequence = nextSequence++;
  pending.push({ sequence, input });
  // sendInput 在重连期间返回 false：直接丢弃这条输入，不排队、稍后不重发。
  const delivered = session.sendInput("input", { sequence, ...input });
  if (!delivered) pending.pop();
}
```

规则：

- `sequence` 只用于回答「哪些输入还没被服务端确认」和「回滚后要重放什么」。它**不是**时间来源，也不是服务端的消费依据：服务端对每条输入最多消费一次（见 [玩法模式](gameplay-patterns.md)），去重靠服务端自己的输入队列与规则，不靠客户端序号。
- 缓冲必须有上限。达到上限时丢弃**最旧**的未确认输入并记一次丢弃计数；无界缓冲既是内存泄漏，也是「越回滚越偏」的源头。
- **断线与重连：清空缓冲。** 游戏在连接断开时停止发送高频输入，恢复后只发送当前输入，不补发过期移动。连接使用原生 Room，见 [纯 HTML 示例](plain-html-client.md)。
- 重连成功后缓冲从空开始，以服务端当前权威快照作为新起点。**不要**从断线前的快照续算，也**不要**重放断线前的输入。

> **现状对照**：`examples/realtime-arena` 的服务端目前只保留每玩家**最新一条**输入（`pendingInputs` 槽位），并不携带序号。带序号的逐条缓冲是本文件的规范形状；落地时需对照已发布 SDK 与上游 v0.18.0 skill 核实 index/ack 字段，再决定是走 SDK 的原生输入确认还是从权威快照推导确认。

## 本地预测

预测只作用于本地表现：用与 `sequence` 关联的输入在本地推进一份**预测状态**，让画面立即响应。

```ts
// 边界草图，需对照上游 v0.18.0 skill 与已发布 SDK 核实 API。
// 预测状态与权威状态是两个对象，绝不互相赋值。
const predicted = new Map<string, Player>();      // 仅本机渲染使用
const authoritative = new Map<string, Player>();  // room.state 的只读投影

function predictLocal(dt: number): void {
  // 与 domain 使用同一条规则，客户端不发明第二套公式
  applyInput(predicted, localPlayerId, latestInput, dt);
}
```

硬规则：

- 预测**永不**写回权威状态，**永不**进入命令 payload、resume handle 或公共 Schema。客户端只提交意图命令，不提交权威状态补丁（见 [SKILL.md](../SKILL.md) 不可协商边界）。
- 预测必须复用服务端 domain 的移动/物理规则。规则漂移会让预测与服务端持续分叉，而客户端无权用漂移后的规则纠正服务端。规则以服务端 domain 为准。
- 预测不覆盖服务端拥有的事实：得分、命中、掉落、随机结果由服务端决定。预测可以乐观地**显示**（例如命中特效），但必须能被随后到达的权威状态撤销。时间的唯一归属见 [架构与归属](architecture.md)。
- 预测层可以随时被整体丢弃并重建——它不承载任何必须存活的状态。一旦你发现某个字段「丢了就坏」，它就不该待在预测层。

## 回滚与重放

收到服务端权威状态后：回滚到权威快照，再重放「服务端尚未确认」的输入。

```ts
// 边界草图，需对照上游 v0.18.0 skill 与已发布 SDK 核实 API。
// acknowledged：权威快照对应的已确认序号（来源见下方说明）。
function reconcile(snapshot: AuthoritativeState, acknowledged: number): void {
  // 1) 回滚：以权威快照为基准重建预测状态，而不是在旧预测上打补丁
  let next = cloneSnapshot(snapshot);
  // 2) 重放：只重放权威尚未确认、且仍在缓冲内的输入
  const replayable = pending.filter((p) => p.sequence > acknowledged);
  for (const { input } of replayable) applyInput(next, localPlayerId, input, dt, next);
  // 3) 丢掉已被服务端取代的输入
  pending.splice(0, pending.findIndex((p) => p.sequence > acknowledged));
  predicted = next;
}
```

**已确认序号的来源**：如果 SDK 不回传逐条输入的确认，就用权威快照携带的服务端 tick/时间推导——早于该快照被服务端消费的输入视为已确认。具体字段需对照已发布 SDK 与上游 v0.18.0 skill 核实，不要凭记忆假定存在某个 `ackedSequence` 字段。

什么时候放弃重放：

- **输入已被服务端取代**：只重放 `acknowledged` 之后的输入，被取代的从缓冲丢弃。
- **超出缓冲上限**：未确认输入超过上限时，放弃继续重放，把预测状态直接对齐到权威快照并重置缓冲。宁可一次硬切，也不让无界缓冲把误差越放越大。
- **重放窗口过长**：`now - oldestPendingAt` 超过阈值时，这批输入大概率已过期；放弃重放，重新以权威快照起算。
- **权威状态不可重建**：快照缺失关键字段时，把预测状态对齐到当前权威投影，不要「猜测」缺失部分。

回滚必须是**纯函数式**的：从快照重建，而不是在上一轮的预测状态上做增量修补——增量修补会把上一轮误差累积进来。

## 插值与外推

渲染时间轴通常**落后于**权威时间轴一小段，用这段缓冲吸收网络抖动：把缓冲里的权威快照在时间轴上滑动插值，而不是一收到就跳到最新值。

- **偏移量（渲染延迟）**：渲染时间 = 服务端权威时间 − `bufferDelay`。`bufferDelay` 在「目标延迟 vs 抖动」之间权衡，典型从 **1–2 个服务端 tick 或约 100ms 量级**起步，再按实测 RTT 抖动调整。本文件不给唯一数值，取值需按实测确定。
- **插值**：在相邻两个权威快照之间做线性/曲线插值。它天然平滑，代价是固定的 `bufferDelay` 延迟。
- **外推**：仅在插值缓冲被耗尽（下一个权威快照尚未到达）时短暂启用，且必须有上限——
  - 时间上限：最多外推约一个 tick；超过就冻结在最后一个权威值，不要无限前推；
  - 幅度上限：外推结果与最后权威位置的偏差超过阈值就停止外推；
  - **不用于战斗判定，不用于计分**，也不写回权威状态——外推纯粹是渲染兜底。
- **禁用外推的条件**：刚刚发生和解（服务端刚纠正过本地玩家）、权威快照间隔已超过阈值、或对象不是本地玩家时，直接冻结/插值，不要外推。

渲染时间轴由服务端时间推导，客户端本地时钟只负责**估计偏移**，不决定结果（见 [架构与归属](architecture.md) 的时间归属）。

## 延迟与网络状态可视化

把网络状态暴露给玩家或调试面板，能让「卡」变成可解释的信息。字段口径与 [测试与可观测性](testing-and-observability.md) 一致。

可暴露的（均为**客户端本地估算**，非权威事实）：

- **RTT**：从输入发出到对应权威确认的往返时间；给中位数与近窗口 P95，不要只显示瞬时值。
- **丢包/迟到**：本地估算的输入丢弃率，以及权威 tick 迟到次数（相邻权威快照间隔超过一个 tick 长度）。
- **缓冲状态**：渲染缓冲深度（tick 数或毫秒）、未确认输入数，以及最近一次硬切的原因。

纪律：

- 这些是本地估算，不是权威事实：不要写回服务端，也不要据此改变游戏规则。
- 不要记录或展示认证 token、私有手牌、隐藏目标或完整入站 payload（见 [测试与可观测性](testing-and-observability.md)）。
- 调试面板默认关闭高频字段的持久化；生产环境只保留有界计数的聚合指标。

## 什么时候不需要预测

预测不是实时游戏的默认配置，而是一个**有成本的选择**：多一层状态、多一套规则复用、多一条和解路径。出现下列任一情况时，直接渲染权威状态即可：

- 玩家动作在收到服务端结果前不推进本地模拟（回合制、棋盘、卡牌、派对投票）；
- 延迟对体验不敏感（异步、单人为主、慢节奏）；
- 预测收益低于它带来的规则漂移与和解复杂度。

判据：如果「画面晚 100–200ms 才动」不会让玩家觉得操作失灵，就不要引入预测。把复杂度预算留给更值钱的地方。
