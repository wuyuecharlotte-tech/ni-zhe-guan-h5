# Web 游戏性能优化

从可复现证据定位瓶颈，按细分维度给出最佳实践、具体优化和验收结果。覆盖游戏循环、渲染、资源、内存、玩法系统及网页宿主；目标是稳定的游玩体验，而非只提高平均 FPS。

## 工作方式

1. **确认环境与目标并启动项目**：从项目读取引擎/版本、2D/3D、后端、发布平台、设备、分辨率/DPR、帧率、画质和典型关卡。用户要求优化且项目可运行时，按 [实测执行流程](references/execution-workflow.md) 发现命令、启动服务、进入真实可玩场景并运行，不能仅输出优化清单。只要求审计时遵循审计范围；真实无法运行时记录阻断并做可完成的静态/局部诊断。
2. **建立并保存基线**：读取 [测量与诊断](references/measurement.md)，固定设备、构建、画质、种子、操作与窗口，验证输入和负载实际生效。按能力选 [采集、场景驱动与统计工具](references/automation-tools.md) 或现有平台工具，保存原始数据、功能断言和失败轮。分别测启动、首次技能、稳态、最坏战斗、切关及长期运行；区分实测、风险、估算和假设，不把不可用填零。
3. **分类再优化**：判定 CPU、GPU、分配/GC、资源驻留、加载、网络、调度或混合瓶颈。一次做能区分假设的实验；不能仅凭 DrawCall 少、heap 回落或平均 FPS 高排除问题。
4. **按需加载维度手册**，不默认把所有手册塞入上下文：

   | 任务 / 症状 | 读取 |
   |---|---|
   | 实际启动、浏览器能力分支、场景重放、修改及回退闭环 | [实测执行流程](references/execution-workflow.md) |
   | 探针接口、Playwright 可选驱动、原始数据与离线分析 | [自动化工具](references/automation-tools.md) |
   | 体验看板、打开速度、操作响应、运行流畅、异常错误率、白屏率 | [体验指标与统计](references/experience-metrics.md) |
   | 全面审计、网页宿主、CPU、玩法、音频、联机、移动端、低动态效果/可访问交互 | [通用与玩法系统](references/common.md) |
   | 2D、Canvas、Sprite、Tilemap、骨骼、文字、粒子 | [2D 专项](references/game-2d.md) |
   | 3D、GPU、模型、材质、灯光、阴影、后处理 | [3D 专项](references/game-3d.md) |
   | OOM、纹理、缓存、GC、场景卸载、资源峰值 | [内存与资源](references/memory-assets.md) |
   | 引擎 API、WebGPU、Unity/WASM、微信适配 | [引擎与平台](references/engines-platforms.md) |
   | 预算、验收、交付格式 | [报告与验收](references/reporting.md) |

5. **实施、复测与回退**：基线保存后，在既有架构内处理已证实的主要瓶颈，保留易回退差异。候选构建重复同脚本与采集配置，比较逐轮长帧、峰值、输入、画质和玩法；无收益或不可接受回归则回退本次改动，再查下一瓶颈。未复测不宣称改善；达到约定预算或收益不足时交付结果与剩余项。

## 全前端优化覆盖盘点

当用户要求“优化整个前端/全面优化/覆盖全部前端优化项目”时，先按下表检查适用性，再依据基线选择改动。覆盖全面表示每一维都有检查结论，不表示每一维都必须改代码。结合项目形态读取相应专项；例如 2D 项目将 3D 标为不适用，微信特有项在非微信项目标为不适用并说明理由。

| 维度 | 最低检查范围 | 主要证据/验证 |
|---|---|---|
| 启动与首局可玩 | 首屏/首场景、首个关键交互、加载阶段和阻塞资源 | 冷/热启动时间、请求与资源瀑布、首局功能断言 |
| 资源加载与缓存 | 拆包/懒加载、压缩与格式、缓存命中、重复或未使用资源 | 传输/解码/上传耗时、缓存状态、资源清单与峰值 |
| 渲染与帧尾 | 主渲染路径、批次/状态切换、过绘、粒子/特效、长帧 | 稳态及最坏场景帧时间分布、帧尾、目标设备画质对比 |
| CPU 与主线程 | 游戏循环、布局/绘制、同步任务、长任务、Worker 适用性 | CPU/主线程时间线、long task、交互期间长帧 |
| 分配、内存与资源生命周期 | 高频分配、对象池/缓存上限、场景切换释放、长期增长 | JS heap 与可用进程/显存数据分开记录；峰值、切换和 soak 检查 |
| 输入、UI 与可访问性 | 输入到反馈、布局/动画成本、事件监听生命周期、键盘/触控与低动态偏好 | 交互延迟、目标状态断言、响应式/辅助操作检查 |
| 网络与请求触发 | 重复请求、轮询/推送频率、序列化/解析、重试与离线/重连 | 单动作请求数与载荷、等待阶段、失败/重试和状态正确性 |
| 兼容与平台差异 | 目标浏览器/设备/API 能力、DPR/视口、降级路径 | 目标矩阵上的启动与关键流程；按能力记录实测，不外推 |
| 长时运行与异常恢复 | 页面隐藏/恢复、切关、断网/重连、资源失败、异常与白屏 | Soak/恢复流程、异常率、恢复后的输入和业务断言 |
| 游戏形态专项 | 2D/Canvas、3D/GPU、音频、联机/Room、引擎/小游戏适配中适用项 | 使用相应专项指标；不适用需注明项目形态依据 |

为每项填写统一状态：`适用且检查`、`不适用（原因）`、`未检查（阻断/范围）`。检查项还须附证据位置、发现或“未发现问题”、验证状态（已验证/仅静态检查/未验证）。不要把“读过该章节”当成检查完成，也不要把无法采集的指标当作零或通过。报告列明覆盖分母：检查完成数/适用总数、未检查项及原因；有未检查项时标注为“部分覆盖”，不得称作全量完成。

若用户说“全量优化”，而不是“全量审计”，仍需盘点所有维度，但只对有基线支持且收益优先的瓶颈实施改动；未改项说明已检查及不改依据。保持游戏玩法、画质、输入和兼容语义，复测与改动相关的端到端场景。聚焦任务则列出实际覆盖维度和明确排除范围，不套用全量声明。

## 输出要求

每项发现对应：`维度 → 证据与置信度 → 原因 → 最佳实践 → 具体修改位置/方案 → 代价与风险 → 验证方法 → 优先级`。按用户请求输出审计、方案或已实施结果，采用 [报告模板](references/reporting.md)。全面审计应标明 2D、3D 及平台维度的适用性；聚焦任务只展开相关维度。

## 必须保留的游戏语义与测量边界

- 降渲染频率、休眠屏外对象或降低 tick 前，检查碰撞、AI、计时器、网络确定性和后台恢复；表现剔除不等于停止模拟。
- 资源卸载按所有权、引用计数或引擎资源管理器执行；共享资源仍被使用时不能销毁。对象池和缓存要有容量及淘汰策略。
- `requestAnimationFrame` 帧间隔不是 GPU 耗时；JS heap 不是进程总内存或显存。GPU/进程数据不可用时如实标记。
- 图集、合批、压缩纹理、Worker、WASM、WebGPU 都有适用条件；以目标设备实测决定，不当作万能优化。
- 参考 log-viewer 的日志/性能/场景/UI 联动思路，不把其 Lua API 当作通用 Web API，不要求安装该插件。浏览器和微信特有 API 先做能力检测。
- 不承诺固定提升百分比；不把 60 FPS、某个 DrawCall 数或微信文档的设备内存阈值当成所有项目的通用标准。
