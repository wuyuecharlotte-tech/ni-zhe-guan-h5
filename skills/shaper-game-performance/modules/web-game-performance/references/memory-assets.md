# 内存、资源与稳定性

## 目录

内存分层与估算；细分优化矩阵；场景生命周期；泄漏/缓存/峰值区分；纹理与颜色空间。

## 1. 先分清哪一层增长

| 层 | 主要内容 | 证据 |
|---|---|---|
| JS | 对象、数组、闭包、监听器、资源句柄 | heap snapshot、retainer path、allocation profile |
| 外部/原生 | ArrayBuffer backing store、解码图像、ImageBitmap、音频、Canvas、宿主对象 | 平台/浏览器工具、对象数量、分配账本；JS heap 可能不完整覆盖 |
| WASM | 线性内存、运行时/引擎 allocator、碎片 | heap capacity 与 allocator 使用量分开记录；free 不代表线性内存或进程立刻缩小 |
| GPU/驱动 | texture、vertex/index/uniform buffer、RT、深度、MSAA、pipeline、驱动副本 | renderer 资源计数、规格估算、GPU/系统工具；通用 Web API 无可靠跨平台总显存读数 |
| 进程/宿主 | 上述部分加浏览器/微信开销及共享内存 | 系统或宿主口径，不能简单与分项相加，避免重复计数 |

估算仅用于预算和比对，不伪装实测：

- 未压缩 RGBA8 纹理基础级：`W × H × 4` bytes；2048² 约 16 MiB，4096² 约 64 MiB。完整 2D mip 链在常见尺寸下约乘 4/3。
- cubemap 再计六面；array/3D texture 按实际层数/各 mip 深度；压缩格式按 block 尺寸和最小块数算，不能套 RGBA8。
- render target 要加 color、depth/stencil、MSAA 存储、resolve 附件及同时存活的 ping-pong 目标；具体分配随后端变化。
- 音频 PCM 近似 `秒数 × 采样率 × 声道 × 每样本字节`，float32 双声道 44.1kHz 每分钟约 20.2 MiB；文件压缩率不能直接推导解码内存。
- 单关资源相加不等于切换峰值：旧场景 + 新场景 + 压缩源 + 解码结果 + 转码 scratch + 上传副本可短时同时驻留。

## 2. 细分优化矩阵

| ID / 维度 | 诊断信号 | 最佳实践 | 具体优化方案 | 验证与取舍 |
|---|---|---|---|---|
| R01 监听器与闭包 | 重开/切场景后对象仍被引用 | 创建者负责注销 | dispose scope 统一解绑 emitter/DOM/resize/input、timer、rAF、observer；取消旧异步任务 | snapshot 保留链、回调次数；不能移除其他系统共享监听 |
| R02 缓存与池 | 对象数量不再用但常驻 | 上限、淘汰、可观测 | LRU/字节预算、空闲池缩容、按场景分组；取消无效强引用 | 稳态平台与命中率；过度清理导致反复 decode/upload |
| R03 纹理分辨率 | 纹理字节占大头 | texel 密度按展示与档位控制 | 按设备供应真实不同尺寸资源、去透明边、拆超大图集、低档纹理预算 | 真机画质/驻留；下载小不代表显存小，CSS 缩小显示不减少已解码图像/源纹理的尺寸 |
| R04 GPU 压缩纹理 | PNG/WebP 小而显存大 | 区分传输压缩与 GPU 格式 | KTX2/Basis 等管线按能力转码到 ASTC/ETC/BC 等实际支持格式；保留兼容回退 | 上传后实际格式、转码峰值、画质；容器不等于必然 GPU 压缩 |
| R05 mipmap | 远处闪烁或纹理浪费 | 按缩小采样需求配置 | 3D/大缩放纹理通常保留 mip；不缩小的 UI 可评估关闭 | 带宽/闪烁/约 1/3 额外基础内存；WebGL1 NPOT 限制须遵守 |
| R06 源图与解码副本 | GPU 上传后 CPU 图像仍驻留 | 明确恢复需求和源数据所有权 | 不再需要时 close ImageBitmap、revoke ObjectURL、释放解码引用；引擎持有源图时遵从生命周期 | 进程与引用；过早 close 会破坏重传、克隆或 context restore |
| R07 几何与 buffer | 模型卸载后资源数上升 | GPU 对象显式生命周期 | 释放无主 geometry/buffer，删除过期 mesh cache；动态 buffer 控制容量/重分配 | renderer 计数与总趋势；移出 scene 不等于销毁 |
| R08 材质与 texture 所有权 | dispose 后别处黑贴图或仍泄漏 | 共享句柄可追溯 | 引用计数/资源管理器；material.dispose 通常不自动销毁共享 texture，逐项核实引擎语义 | 跨关共享、重复卸载；禁止无脑遍历 dispose 一切 |
| R09 RT、Canvas 与尺寸 | 横竖屏/后处理开关后内存涨 | 复用且释放旧附件 | RT pool 按规格/字节限制，resize 后销毁旧资源，清理离屏 canvas | 往返尺寸后计数平台；很多小 RT 也可能碎片化 |
| R10 解码/转码峰值 | 载入模型时 OOM | 输入与临时内存纳入预算 | 限制 decoder/worker 并发，分批资源，及时回收中间 buffer；meshopt/Draco 按实际成本选择 | 峰值/可玩耗时；压缩更小可能解码更慢 |
| R11 GC 与分配率 | 周期性卡顿、回收频繁 | 减少源头垃圾与长期引用 | 热点复用、拆大任务、限制日志；大型释放放在可接受切换点并测峰值 | GC pause/alloc rate；标准浏览器 JS 不可依赖手动 GC |
| R12 WASM heap 与碎片 | 释放资源后 heap 容量不降 | 容量与实际使用分开 | 调整资源生命周期、批次与合理初始/增长策略，复用大块缓冲；按引擎构建配置验证 | 使用/容量/进程三条曲线；过大初始内存也可能启动失败 |
| R13 音频与媒体 | 音乐切换占内存、node 累积 | 载入/解码/播放/释放分层 | 复用解码 buffer、有界 voice；停止并断开无用 node，释放旧引用 | 播放功能与内存；关闭全局 AudioContext 前核对共享者 |
| R14 场景交接 | 新旧关同驻留峰值过高 | 峰值预算优先 | 可选过渡场景：停止旧生产者→卸载非共享资源→分批加载新关；也可保留小共享集 | 切换峰值/黑屏时长/首帧；不要求所有游戏采用同步卸载 |
| R15 异步取消与过期结果 | 离开场景后资源又被回调挂回 | 请求与场景 generation 绑定 | AbortController/loader cancel，结果到达核对 generation；过期结果释放/归还资源管理器 | 快速切场景/失败重试；不能只忽略结果却不释放大数据 |
| R16 低内存降级 | OOM/平台告警 | 告警是补充，主动预算为主 | 丢弃可重建缓存、低档纹理/RT、取消预取；保留关键逻辑状态与诊断 | 真机压力与恢复；浏览器无普遍可用内存告警，微信检测 API 能力 |
| R17 资源加载失败 | 重试导致重复分配/卡死 | 有界重试与幂等状态 | 清理失败中间资源，退避重试、占位与降级；同资源请求合并/引用管理 | 断网、404、解码失败；避免无限队列 |

## 3. 场景生命周期合同

资源账本字段建议：`id/type/owner/refCount/state/estimatedBytes/sourceBytes/lastUsed`。区分共享常驻包、场景专有包、临时工作区和可重建缓存。

典型卸载顺序按引擎调整：

1. 标记场景退出，停止新 spawn、预取、AI 作业及异步挂接；取消或隔离在途回调。
2. 注销事件、timer、ticker、UI 绑定、音频实例、物理对象、网络订阅；从活跃集合移除。
3. 归还池对象并清除场景引用；按资源管理器减少引用，只释放最后一个使用者已退出的 GPU/音频/原生资源。
4. 清除场景专有缓存、临时解码数据；共享纹理/材质继续存活。确认 context restore 或重新载入路径仍有数据来源。
5. 复测场景往返、功能与资源计数；JS GC 与驱动回收有延迟，记录回落窗口而非要求立刻回到零。

## 4. 区分泄漏、缓存与一次性峰值

- **强证据泄漏**：等价场景反复进出，存活对象/资源数量或被保留字节持续增长，并能定位无用引用/未释放资源。
- **受控缓存**：预热后增长趋平、存在明确上限与淘汰，且降低加载延迟；需与设备预算兼容。
- **峰值问题**：稳态正常但加载/切换瞬时超过容忍范围；改并发和重叠生命周期，不能仅看均值。
- **容量/驱动保留**：WASM capacity、浏览器 allocator、GPU 驱动可能维持高水位；不能只因进程不回到起点就断言泄漏，也不能据此忽略持续增长。

建议以 20 次等价关卡往返作为初始压力脚本，必要时加长到观察出平台或持续斜率；记录每轮相同停留点的 JS、资源账本、WASM 与可得的进程数据。生产验收不依赖 DevTools 的强制 GC；诊断快照可用受控 GC 辅助比较，但须注明。

## 5. 纹理与颜色空间检查

颜色贴图与线性数据贴图应遵守引擎颜色空间配置。normal、roughness、metallic、AO 等数据通道打包时验证色彩转换与压缩误差；alpha、边缘 padding、mipmap bleeding、HDR 格式、filter 和 wrap 均属于资产验收。KTX2/Basis 转码与 mip 生成要比较首局耗时、临时 CPU 内存、GPU 最终驻留和低档机画质，不能只报告网络包缩小。
