# 体验看板指标与游戏专项映射

用于用户提供体验看板、线上趋势、错误/白屏报警或要求改善整体体验时。先取得看板的指标定义、SDK/平台版本、统计周期、设备分组、分子分母、样本量、聚合方式和采样率；仅凭名称及截图不能确认官方口径。没有定义时，下面是本项目可采用的自定义口径，必须标注「自定义」，不能冒充平台指标。

## 五类指标

| 看板指标 | 游戏内对应量与采集 | 最佳实践与优化方案 | 验证与边界 |
|---|---|---|---|
| 打开速度 | 入口导航/宿主启动 → 引擎初始化 → 首关关键资源就绪 → 首帧提交 → 可接收有效输入；分别记阶段和总耗时。网页可补充 Navigation/Resource Timing、FCP/LCP，宿主用其启动性能工具 | 缩短首局依赖链；代码/关卡分包；缓存版本一致；下载、解码、上传有界并发；分批 shader 预热，后续资源延后。参见 common 的 W01–W05、内存资源手册 | 冷/热启动及网络档位分别测 P50/P75/P95、失败数与样本量。Canvas 的可玩不能由 DOMContentLoaded、canvas 存在或 LCP 单独证明。可玩超时的失败不能从成功样本中悄悄消失 |
| 操作响应 | 输入时间 → 逻辑消费 → 技能/移动状态真正改变 → 对应渲染提交；同一 actionId 关联。DOM UI 支持时用 Event Timing/INP，Canvas/引擎另加 hook | 缩短主线程长任务；输入队列有界；及时消费输入；减少逐帧 DOM/React 重渲染；调整 tick/插值与网络等待；保持输入语义，不能统一节流触控。参见 common 的循环、输入和联机维度 | 分别报输入到逻辑、到提交 P50/P95/P99；真实输入到光子依靠呈现测量/高速摄影。INP 的页面级聚合并非所有点击的平均值；不能把某次事件耗时或测试框架 click 返回时长当 INP |
| 运行流畅 | 帧间隔分布、超预算比例、连续卡顿、长任务、CPU/GPU 分段；B=1000/目标FPS，自定义超预算率=超过 B+容差的间隔数/有效间隔数 | 先做 CPU/GPU/GC/加载分诊；2D 查合批、图集、粒子、Tilemap、文字；3D 查剔除、LOD、材质/shader、阴影、过绘和后处理；再检查物理/AI/动画、热降频 | 看板百分比可能代表慢帧、卡顿时长或慢会话比例，需查平台定义，不能直接等同自定义超预算率。稳定、首次技能和最坏战斗分开；rAF 不是实际呈现 FPS |
| 异常错误率 | 建议自定义「发生至少一次指定异常的唯一会话数/可观测有效会话数」，同时报告错误事件数、错误会话数与总会话数；定义 session 边界与去重规则 | 引导脚本尽早建立有界错误监听；关联版本/场景/actionId/资源ID/调用栈；分 JS error、未处理 Promise、资源失败、WASM trap、context/device lost、宿主异常。修根因，配置匹配版本的 source map；限次重试并给恢复路径 | 多个错误事件不重复增加会话分子；资源失败与 Promise 不能重复算同一根因的事件。采集脚本没加载、进程被杀或离线不等于无错误；不能直接监听到 OOM，需宿主/系统证据。关闭上报不能算优化 |
| 白屏率（游戏也包括非预期黑屏） | 建议自定义「启动后超过场景时限仍无有效首场景，或游玩中持续失去有效画面的唯一会话数/对应可观测启动或游玩会话数」；启动白屏与中途黑屏分开 | 联合引擎 ready、关键资源结果、游戏状态/心跳、首帧提交和必要截图；查 JS 启动异常、包版本错配、缓存、资源404/CORS/解码失败、WASM加载、渲染上下文丢失、canvas 尺寸0、遮挡和生命周期恢复；超时可恢复/重载应有界 | 空白 DOM 不证明 Canvas 白屏；纯色截图可能是合法场景；有 canvas 不证明渲染成功。先设非空且可输入的场景断言，再用截图辅助。像素读回可能受跨域限制且引入 GPU 同步，不逐帧执行；后台暂停、合法转场/加载与进程终止单独分类 |

截图示例中的参考线为打开速度 ≤2.5秒、操作响应 ≤200ms、运行流畅项 ≤3%、异常错误率 ≤1%、白屏率 ≤0.1%。这些只作为该看板显示值记录；未取得其定义前，不将其写成通用 Web/微信官方标准，也不保证本地统计可以还原该看板。体验评分及「良好/较差」等级依赖平台权重/算法，未知时不自行合成相同分数。

## 采集与汇总合同

- 为每项记录 metricName、definitionVersion、unit、起止边界、分子/分母、百分位或聚合方法、观察时长、环境、构建、采样策略。GPU/内存等指标保留 measured/estimated/unavailable 标记。
- 建立本地可复现场景与线上 RUM 两条证据链。本地三轮测试只能说明这些场景，不能生成真实线上白屏率/错误率或用户体验评分。接入线上采集时复用已有管线；若无管线，交付方案及本地验证，不擅自建外部上报服务。
- 错误收集早于主游戏 bundle：`error` 区分 ErrorEvent 和捕获阶段资源失败事件，`unhandledrejection` 收集未处理 Promise；使用固定容量、聚合指纹和限流，避免 stringify 大对象。跨域脚本可能只有 Script error，不能编造堆栈；上传 source map 的权限与资产策略沿用项目要求。
- 自定义白屏状态机可为 `starting → playable → interrupted/recovered/failed`。项目定义 startupTimeout、blackoutDuration、排除状态和恢复成功条件。主线程完全阻塞时，同线程 watchdog 也不能及时执行，恢复后须结合时间戳/长任务，不能宣称实时检测全部冻结。
- 会话聚合示例：1000 个可观测会话，8 个会话发生共20次异常，错误会话率=0.8%，事件数=20；并非2%。另有5个启动白屏，启动分母若为900次可观测启动，则为5/900，不能沿用1000会话。未知/失联样本另列，报告观测覆盖率。
- 对不同平台/设备/网络/场景/版本分组；先累计分子分母再算率，不能对各组百分比简单平均。报告零分母为不可计算，少样本的0%不代表可靠；抽样或故障上报丢失有偏时说明限制。按日/版本看趋势并保留发布标记，避免总体改善掩盖低档机回退。

## 从看板进入修复闭环

1. 读取异常时间段与设备/版本分布，导出原始聚合与若干关联日志；不在报告中暴露凭据/用户私密数据。
2. 将用户最差路径变成固定场景：例如「冷启动 → 第一次释放技能 → 切关 → 后台恢复」，分别给启动、响应、流畅、异常和有效画面断言。
3. 按 [执行流程](execution-workflow.md) 实际运行，保存失败轮、trace 和截图。优先修影响可玩性的错误/黑屏，再优化关键耗时。
4. 同版本口径、同负载复测，并回归离线、404、版本更新、context/device lost 等相关失败路径。若发布不在授权范围，只交付本地结果和建议的线上观测门槛，不自动发布。
