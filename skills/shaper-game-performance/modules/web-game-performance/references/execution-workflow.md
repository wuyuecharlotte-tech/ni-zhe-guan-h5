# AI 实测、修改与复测执行流程

适用于用户要求「优化当前游戏」「跑数据后优化」「修复卡顿/内存/加载问题」。先读本流程，再按症状读专项手册。用户只要求审计时，实际采样和临时诊断遵循审计范围，输出证据与方案；不要因此擅自改产品行为。工具命令与原始格式见 [自动化工具](automation-tools.md)，线上体验指标见 [体验看板](experience-metrics.md)。

## 1. 发现项目并建立可运行环境

1. 读取项目说明、适用的工作区指令、引擎版本、package.json/scripts、锁文件或引擎构建配置。记录 Git 构建标识及未提交补丁标识；无 Git 时用构建目录/清单哈希。先保护用户已有改动。
2. 确认已有服务及依赖，使用项目规定的包管理器与锁定版本；不要猜 `npm run dev`，不要为诊断顺手升级引擎或重装全部依赖。需要依赖时按当前工具权限处理，并记录真实阻断。
3. 根据脚本/文档选择发布构建与预览命令。开发构建便于定位，但 HMR、断言、sourcemap 与调试面板会改变性能；正式前后验收使用同模式。若构建失败，只修与本任务相关且可回退的必要问题，保留完整失败日志。
4. 在持续终端启动服务，保存命令、cwd、端口、URL、PID/会话ID与 stdout/stderr。根据实际日志确定就绪地址；HTTP 成功后还须进入游戏验证，不能只看端口已监听或 canvas 标签存在。
5. 复用合适的现有服务，但记录其构建来源；测试结束只停止本次自己启动的服务，不批量 kill 用户进程。

## 2. 盘点工具能力并选择路径

| 实际能力 | 执行路径 | 必须注明的限制 |
|---|---|---|
| 浏览器操作 + 页面 JS + 文件导出 | 复用已有浏览器工具/项目测试框架，注入 browser_probe.js 后采集；已有 Playwright 可用附带驱动 | 不预设存在 CDP、Chromium 或独立浏览器。API 支持先检测 |
| 仅浏览器/UI 操作 | 用浏览器/引擎 profiler 或已有调试面板导出文件；可在项目开发构建加临时低开销开关 | 无法注入/导出则记录实际截图和工具读数，标注采样方式，不能编造 JSON |
| 有 CPU trace / GPU profiler | 按热点另录 Performance trace、引擎 profiler 或 GPU 帧捕获 | Playwright 操作 trace 是动作记录，不等于 CPU Performance trace；截图/录屏不是 GPU 耗时 |
| 微信小游戏/特殊 WebView | 按平台和引擎支持的工具、真机运行与导出；复用相同场景合同 | 不强行注入 DOM/rAF/Playwright API，不把桌面数据替代宿主真机内存 |
| 本地预览或某个浏览器工具失败 | 先检查其他现有浏览器/UI 能力；宿主有已上传预览、授权与远程日志时，按总入口的平台适配转入该调试路径；核对实际加载版本 | 旧预览只验证旧版本；远程日志/接口通过与页面交互通过分开记录 |
| 当前游戏仍无法运行 | 完成构建/静态审计、资源账本、可运行子场景及不依赖页面的后端源码验证；输出具体错误、已尝试路径与剩余步骤 | 结论按证据标注；缺 GPU、页面或平台身份只限制相关验证 |

优先现有能力，不为统一工具而引入一套新框架。工具不可用时选可行分支继续；只有真实缺失且影响结论的信息才需要用户补充。

## 3. 把游玩路径写成场景合同

每个场景保存场景ID/版本、种子、初始存档/关卡、对象数量/质量、镜头和操作序列、网络脚本、窗口起止、重置方法、成功与失败断言。人工操作也记录步骤与时间线，不能把不一致操作混成一组。

- **可玩门槛**：引擎就绪、关键资源完成、目标关卡状态正确、画布尺寸正确，并能响应一项真实有效输入。优先读项目状态/现有调试接口，必要时加可移除的开发 hook。
- **负载门槛**：断言敌人/粒子/技能实际存在，镜头路径完成、碰撞/伤害/得分等真实变化。自动化的 click 成功只表示动作送达；若未验证游戏状态，可能只是录到了菜单或空场景。
- **首次与稳态**：首次技能测量前不能先用同技能暖机，窗口覆盖输入前到首次效果完成；稳态先预热再同页重置状态，保留已预热资源。场景重置不能悄悄重新加载页面或清资源，除非该场景明确要求。
- **缓存协议**：独立 browser context 只隔离部分站点状态，不等于 OS、HTTP 中间层、浏览器 GPU/shader 缓存全冷。首次生命周期、冷进程、清缓存、热启动分别命名；真实冷启动另用有记录的环境协议，不能只依赖 fresh-context。
- **观察窗口**：稳态可从每轮30–60秒、重复3轮起步；首次事件用独立短窗口，不让几十秒平均稀释一次长停顿。内存切关可先20轮，热稳定性从10–30分钟起步并分块保存，按问题调整。
- **测量边界**：第一条到第二条回调才有完整间隔，start→首回调及末回调→stop不伪造为帧。长任务按窗口裁剪。隐藏/resize/溢出/输入失败保留失败证据；刻意测后台或resize时改用专项报告，不能混进稳态结果。

## 4. 先保存有效基线

1. 实际进入场景，检查 ready 与负载断言。选择代表设备与发布构建；固定刷新率、viewport、drawing buffer、DPR、renderScale、画质、目标FPS、网络及热状态。
2. 启动有界采样；首次动作前等采样器取得至少一个完整帧间隔（附带探针isReady），或确认所用profiler已开始记录，然后再操作。等待期间不提前释放技能；否则阻塞可能落在start→首回调的未知间隔。可用时分别记录游戏整帧提交、CPU阶段、引擎计数器、GPU异步计时、JS/WASM/宿主内存。详细捕获可单独诊断轮完成，避免每次采样都挂高开销调试工具。
3. 执行真实操作，记录 input/action/scene/frame 标识。输入到逻辑、渲染提交、实际呈现分别命名，不能混用。
4. 停止并导出原始数据，保存功能断言、构建/环境清单和结束后的截图；需要对应瞬时现象时另录关联帧/trace。比较探针开/关开销，过高则降采样或另设诊断轮。
5. 离线统计逐轮 P50/P95/P99、最大间隔、超预算率、连续超预算长度、峰值和资源趋势。少样本/少于3轮仅探索；不通过删掉最慢轮或GC长帧来「清洗」。失败轮保留并查因；修复后整组重跑。

原始目录建议：`perf/场景/构建/设备/baseline/`，保存 `run-*.json`、截图、trace、环境说明、运行日志、场景与配置版本；候选结果放独立 `candidate/`，报告放 `comparison/`。不覆盖原始轮次，截图和profile关联到同一run编号。

附带工具只自动采集回调/可选游戏提交节奏、支持时的 longtask、可选JS heap及自定义数值；不是完整 CPU/GPU/输入/白屏监控器。项目级接入方法见 [自动化工具](automation-tools.md)。

## 5. 分诊、区分实验与最小修改

- 用 trace 与 [测量手册](measurement.md) 的区分实验判定 CPU/GPU/GC/加载/网络/内存驻留。降分辨率、关闭阴影或临时停AI是定位实验，修改画质或玩法后的数据不能作为同质量优化的验收组。
- 形成一条可证伪假设：`场景 → 热点证据 → 原因 → 修改位置 → 预期改善量 → 可能代价 → 反证条件`。按影响与成本优先，避免未分析就迁移引擎、改Worker/WASM或全面合批。
- 一次提交一个有解释性的改动组，保存差异与回退方式。对 CPU、GPU、内存、启动、画质、玩法和输入链路的交换分别检查。
- 没有归因证据时先做最小区分实验，再实施；有明确局部热点时不为流程增加无意义的实验。

## 6. 同场景复测与验收

1. 候选构建使用相同场景脚本、种子、预热策略、质量和采集工具，完整重复运行；只有构建标识和改动内容应变化。必要时交错基线/候选并再次测基线，以区分温升和环境漂移。
2. 核对环境/负载字段，查看逐轮波动；统计脚本提示不可比时，不宣称改善。实际窗口延长可能是真实主线程卡顿，也可能是脚本等待，保留全量数据检查原因，不能裁掉停顿。
3. 若P95改善但P99/最大间隔、启动峰值、长期内存或输入变差，报告取舍并评估；跨阶段转移成本不算问题已消失。收益处于轮间波动内时标记不确定并作有针对性的重复。
4. 回归功能、相机/阴影/粒子/文字画质、碰撞/伤害/AI、动画事件、音频、联机与存档等相关路径；有项目现成构建/类型/测试要求则执行。物理/调度/释放语义变化需相应回归，纯参数调整不必新增镜像实现测试。
5. 确认改善且无不可接受回归则保留；无收益/成本过高则回退本次改动并保存实验结论；不要回退用户其他改动。再选下一个瓶颈，达到约定预算或收益不足时结束，不无限循环。
6. 清理本次临时hook、overlay、订阅和缓存，或转为默认关闭的开发功能；移除诊断后至少检查可玩与必要核心指标，避免误删导致性能或功能回退。只清理自己创建的服务/资源。

## 7. 交付与真实阻断

使用 [报告模板](reporting.md)，列出实际启动/采样/统计命令、场景合同、所有原始文件位置、逐轮前后结果、已改与已回退项、功能画质证据、未测设备/指标及原因。没有权限、真实设备、GPU计时或运行条件时，说明这限制了哪个结论，并继续其他可完成部分。用户只要求文件或本地修改时，到可审查结果为止，不自行安装skill、发布游戏或上报外部平台。
