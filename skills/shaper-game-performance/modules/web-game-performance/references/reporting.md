# 报告、预算与验收

## 1. 审计报告合同

先给主要瓶颈、证据强度、影响场景与下一项能区分原因的实验。静态审计写「风险/待验证」，实测写具体设备、构建与采样口径。不要把整个优化手册原样复制成报告。

### 项目与目标

- 引擎/版本/后端；2D、3D 或混合；目标浏览器/小游戏宿主、设备档位、刷新率、分辨率、DPR 与画质。
- 目标 FPS 与场景预算；首局可玩定义；内存稳态/峰值、资源数量上限与可接受画质变化。
- 场景脚本、随机种子、预热/冷启动、测试窗口、重复次数、温度与网络条件。
- 可用工具与缺失数据；本次审计覆盖/不适用/未验证维度。
- 实际构建/启动/采样/统计命令及cwd、服务URL、场景与适配脚本版本、原始JSON/trace/截图/日志的路径；所有失败轮及失效原因。窗口偏离时保留真实停顿并解释，不静默剪裁。
- 如涉及体验看板：按 [体验指标](experience-metrics.md) 写定义版本、分子分母、样本量、采样覆盖率、线上/本地来源、按日或版本趋势；未知平台算法不还原体验评分。

### 逐项发现表

| 优先级 | 维度 ID / 位置 | 证据及置信度 | 原因/假设 | 最佳实践 | 具体优化方案 | 收益指标 | 代价/回退 | 验证 |
|---|---|---|---|---|---|---|---|---|
| P1 示例 | D03，爆炸 emitter/材质 | 实测：固定脚本降特效 RT 分辨率后 GPU 降，CPU 近似不变 | 特效像素成本高，shader/带宽仍需区分 | 按覆盖面积限制特效 | 本效果 RT renderScale 分档；保持碰撞与伤害逻辑 | P95/P99/GPU ms/峰值 RT 字节 | 辉光清晰度；开关回退 | 同一爆炸脚本与截图比较 |

收益指标列写要改善的量；没有数据时不填虚构百分比。实施后补真实前后数值。文件位置必须实际存在，不能编造行号或调用栈。

优先级建议：

- **P0**：可复现 OOM、严重泄漏、无法游玩或丢失必要状态。
- **P1**：核心场景持续不达预算、明显长帧/延迟、启动阻塞。
- **P2**：边缘场景、容量余量、可证实但影响较小的问题。
- **P3**：待证据支持的实验、复杂度较高的后续方案。

再综合影响用户比例、复现概率、收益证据、工程成本和画质/玩法风险排序；高成本架构迁移不因理论收益优先。

### 优化前后对比

| 场景/设备 | 构建 | FPS | P95/P99 间隔 ms | 超预算率/容差 | CPU/GPU ms | 稳态/峰值内存及口径 | 可玩耗时 | 质量/玩法 |
|---|---|---|---|---|---|---|---|---|

缺失数据填「未测/不可用」，估算标「估算」。改 targetFPS、renderScale、效果质量时写出前后配置，不能只给优化后的 FPS。

每个场景附逐轮结果及轮间中位数/范围，rAF回调、游戏提交与实际呈现分开命名。环境/质量/负载不同则写不可比，不宣称同质量收益；少于3个有效重复为探索性。离线工具只能辅助比较，不能自动证明画质、玩法或线上错误率改善。

## 2. 验收场景

| 类型 | 适用项目 | 通过依据 |
|---|---|---|
| 冷启动、热启动、首次技能/首次 shader | 所有游戏 | 首局可玩符合预算；首次使用不被稳态平均值掩盖 |
| 最大战斗/弹幕/粒子 | 动作、射击、战斗游戏 | 帧尾延迟和超预算率改善，伤害/碰撞/音效一致 |
| 密集 UI、多语言字体、列表滚动 | UI 密集游戏 | 布局、字形、点击与视觉正确，内存/长帧稳定 |
| 镜头快速移动、大地图流式 | 地图/3D 项目 | 无加载洞、剔除错误、峰值失控；可见量与耗时匹配 |
| 反复切关、死亡重开、退出重进 | 有场景生命周期的项目 | 建议先 20 轮相同路径；资源/内存进入有界平台，引用链合理 |
| 10–30 分钟持续游玩起步 | 移动端/热降频问题 | 按实际风险调整时长；记录冷/热状态，持续帧率与内存不过度退化 |
| 后台/前台、resize/context/device lost | 支持相关能力的项目 | 无追赶风暴、重复循环、黑屏、资源持续增长 |
| 弱网/断网/失败重试/重连 | 联机或在线加载 | 队列有界，关键事件恢复正确，无重复实例/资源 |
| 低动态效果、键盘/触控/手柄与替代 HUD | 有相关设置或受此次优化影响的项目 | 必要危险提示、输入语义、焦点和状态播报保持正确；替代 UI 不产生逐帧 DOM/播报开销 |

## 3. 完成条件

1. 同配置、同脚本比较，采样窗口与样本量足够解释 P95/P99；改善超出常规波动，或明确尚不确定。
2. 关键画质、输入手感、碰撞/AI/动画事件、联机同步、音频及存档无已知回归；帧率提升若来自降画质须明确说明。
3. 峰值、稳态及资源生命周期均检查，不能用平均 heap 取代 OOM/显存验证。
4. 项目适用的构建/类型检查/已有功能验证通过；如改物理/时间步/资源释放，补对应的有意义回归验证。无需为纯参数微调编造只镜像实现的测试。
5. 报告列出已改、已验证、未覆盖、残留风险与回退方法；工具/设备缺失时只宣称实际完成的范围。

## 4. 使用示例

- 「用 $web-game-performance 审计当前 Phaser 游戏，重点检查大量敌人和爆炸时的长帧，先给有证据的修改顺序。」
- 「用 $web-game-performance 优化 Three.js 场景，保留既定画质，分别测 CPU 提交、阴影和后处理，不要直接合并整张地图。」
- 「用 $web-game-performance 检查 Cocos 游戏反复切关后的内存，输出资源所有权、峰值、泄漏证据和可验证修复。」
- 「用 $web-game-performance 为 Unity WebGL 的低档手机制定首局加载、WASM heap、纹理与 shader 变体的预算和验收脚本。」
