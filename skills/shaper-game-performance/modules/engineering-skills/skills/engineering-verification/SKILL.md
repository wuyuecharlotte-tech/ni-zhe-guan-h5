# 证据驱动的实现验收

先说明待验证命题，例如“列表增长不会增加逐项数据库调用”或“交易后的晚到旧读不会覆盖新状态”。选择能在错误实现上失败、正确实现上通过的证据；按改动风险控制范围，不为纯文案或低影响改动制造复杂测试。

## 把设计映射到验证

| 改动机制 | 有意义的证据 | 仍不能证明什么 |
| --- | --- | --- |
| 合并或批量查询 | 按动作/视图统计调用次数，改变列表规模；核对SQL计划与处理行数 | 一个RPC不能证明内部计算便宜 |
| 缓存与在途合并 | 同key并发过期、跨身份/参数隔离、失败释放、容量饱和 | 单实例通过不证明多实例协调 |
| 写后刷新 | 用可控屏障安排旧读、写提交、新读及响应顺序 | 固定sleep偶然通过不证明竞态正确 |
| 交易重试 | 同业务键重复/并发执行，余额持仓等不变量保持；参数冲突可识别 | mock事务不能证明真实PG锁语义 |
| 过载隔离 | 慢依赖占满一个通道时，核心通道仍可服务；超时和清理有界 | 本地容量不等于平台配额 |
| 快照与增量 | 输入不变不重复聚合，输入改变更新版本，最大陈旧有界 | 功能测试不证明生产后台容量 |
| 前端减请求 | 一次动作/路由切换请求数、隐藏/恢复、失败重试、切账号和写后更新 | 请求减少不代表首屏体验一定更好 |

优先通过行为、依赖调用或真实隔离数据库验证；文本匹配、断言常量和全mock返回不能代替对应行为。同步修改契约与夹具时保留测试原有保护目标，不用删断言掩盖问题。

## 证据分层

区分代码推断、静态检查、单元/集成测试、实际环境观察、负载结果。只声明当前证据能支持的范围。无法运行某层验证时完成其他可行工作并标注缺口，不补写虚构的吞吐数字。

性能对比核对版本、配置、数据规模、身份与热点分布、缓存冷热、请求比例、时长和客户端能力。尽量一次改变一个关键因素；多项同时修改时只归因到组合效果，除非有额外隔离证据。多个实例/时段的分位数不能简单平均成总体P99。

日志沿调用链记录适量的请求标识、版本、路径、缓存状态、RPC次数、排队与阶段耗时、响应字节和资源指标。使用低基数指标及采样，保护身份/令牌/账本内容；高频逐请求全量日志本身也有成本。

## 完成与长期防退化

运行项目实际规定的相关检查，审阅输出和失败；验证修复针对原始触发场景。已有失败与本次引入的失败分开证明，重跑成功不擦除首轮不稳定结果。

用户授权发布时，确认实际部署版本、配置、鉴权和业务结果；控制面返回成功不替代配置回读。若涉及前后端协议变化，说明兼容窗口和发布顺序。提供回滚范围，数据库变化需单独评估兼容性。

结束时报告：改动的因果机制、实际验证结果、未覆盖场景和剩余风险。没有压测能力时可通过查询预算、执行计划、并发时间线和故障注入提升可信度，仍注明吞吐未验证。

将有复发价值的约束加入测试或公共组件契约；架构决策只保留理由和取舍。避免把某次测得的实例并发、TTL或机器规格固定为所有业务的标准。
