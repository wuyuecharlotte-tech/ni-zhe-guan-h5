# 工作量建模与瓶颈分析

以用户动作和实际路径为分析单位。先读代码、配置、请求/查询记录；没有环境数据时做带假设的设计估算。仅修改单个接口也要检查其上游触发和下游工作，避免局部优化把成本搬到别处。

## 建模

选取本次关键场景：首次打开、常驻刷新、写后刷新、热点或批任务。记录用户动作频率、请求扇出、数据规模/倾斜、身份分布、响应字节，以及前端重试和轮询。每项标注观测来源或假设。

按路径、读写和命中/未命中分开估算：

- 下游调用率 ≈ 动作率 × 请求扇出 × 回源比例 × 每次回源调用数，另外加独立写入与后台任务。回源合并按有效合并后的数量计算。
- 扫描/计算成本还取决于每次调用处理的数据量；一个 RPC 内可以隐藏 N 次查询或全表聚合。
- 带宽 ≈ 响应率 × 实际线上响应字节；传输压缩不等于堆内存节省。
- 稳态平均在途数 ≈ 到达率 × 平均停留时间，使用同一系统边界和单位。它不能用 P99 替代均值，也不能单独给出安全并发值。

完成建模的标准是指出主要成本随什么变量增长、最敏感的假设是什么，以及哪些资源可能先饱和。详细测量口径见 [测量与容量](references/measurement.md)。

## 源码可得、生产测量不足时

先画出关键操作的实际调用顺序，并定位循环、同步任务、缓存与等待边界。选优先风险，用实际模块和受控依赖做小实验：冷缓存并发请求统计实际回源次数；让依赖暂不完成，检查持久化后的响应还在等待哪些步骤；按输入规模测解析/解压/计算；按不同键和过期周期观察缓存是否有容量上限与淘汰。实验隔离外部服务、保存脚本、输入和原始结果，恢复所有临时探针。只读审阅允许此类隔离诊断；明确仅静态时不运行。

区分三层结论：源码说明潜在机制，隔离实验确认给定条件下的机制，真实环境观测确认线上影响。少量快日志只能描述所采样请求；没有线上样本时，报告已复现的放大/等待关系及待测影响，不直接估计线上 P95、QPS 或百分比收益。涉及 SQL 的结论需查询实现/执行计划；依赖替身不证明数据库执行快慢。

## 从机制选择改动

先问这项工作是否必要，再按情形选择：

- **重复触发**：检查组件挂载、路由切换、隐藏页面、重试链。复用请求、按需读取、合并刷新；保留加载/失败状态和写后刷新语义。
- **重复计算**：检查输入变化频率与读取频率。考虑按版本或增量生成、共享快照；后台任务也要有输入规模与成本边界。
- **往返放大**：批量查询、最小字段、分页；同时核对 SQL 的扫描、排序与锁成本。
- **缓存失配**：检查用户/租户/参数/版本范围，冷实例和过期回源。进程合并只作用于一个进程，横向扩容可能使总回源变多。
- **响应处理重**：用证据区分查库、序列化、压缩、网络和渲染。考虑复用编码结果、减字段、分页或增量；同时检查前端重复解析和大列表渲染。
- **资源饱和**：定位队列、CPU、内存、连接、锁或平台限额。并发、连接池、实例数和下游预算共同调整；先确定瓶颈再决定增大还是减小。

每项方案说明前后工作量如何变化、成本转移到哪里、业务需要怎样配合。缓存、异步化、并发和重试变更进入 [一致性与故障设计](../engineering-reliability/SKILL.md)。

## 实际诊断

先建立客户端端到端、网关、函数内处理、排队、RPC往返、SQL执行的时间分解。用请求标识、时间窗和版本关联；并行阶段按关键路径解释，不能简单相加。

形成具体假设并选能区分原因的观察或最小实验。例如 SQL 快而端到端慢，应检查排队、网络和响应处理，而不是继续添加索引。平台错误码本身不足以证明冷启动、QPS 限额或连接故障。

在用户任务范围内实施，按 [证据与回归](../engineering-verification/SKILL.md)验证。交付主要放大因素、预期变化、实际变化和剩余不确定性；没有负载测试仍可交付分析与局部验证，但吞吐保持未验证。
