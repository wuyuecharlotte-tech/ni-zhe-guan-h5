# 场景驱动的工程设计

目标是把业务要求变成有成本边界、正确性约束和失败行为的实现。输出可核查的设计理由，不要求展示内部思维过程。深度随风险变化：局部改动可用几句话完成；跨层数据流、交易、共享状态或高峰流量需要完整分析。

## 建立当前事实

先读项目规则、受影响的代码、测试和已有公共能力。改进现有系统时追踪实际实现；新系统先列假设。按用户动作描述成功条件，区分展示与权威状态、可延迟工作与必须完成的工作。需求、代码和部署不一致时明确标出证据来源。

追踪一条完整链：用户动作 → 前端触发/轮询/重试 → 接口 → 缓存/后台任务 → 数据库 → 返回/渲染。列出每条路径的读写副作用，GET、名为 read 的函数和缓存命中都不能代替实际检查。结束条件是知道关键工作由谁触发、为何发生、谁消费其结果；未知环节列为待验证项。

## 推导设计

1. **找放大关系。** 识别成本随用户数、数据量、热点、刷新频率、实例数或重试次数如何变化。需要容量估算、前后端协同或性能诊断时，读取 [工作量建模](../engineering-workload/SKILL.md)。先判断不必要的工作，再考虑加速剩余工作。
2. **守住业务语义。** 为受影响数据说明权威来源、允许陈旧程度、写后可见性及隔离范围。涉及交易、缓存失效、异步处理或依赖故障时，读取 [一致性与故障设计](../engineering-reliability/SKILL.md)。涉及产品取舍且无法从现有事实推断时才询问用户，并给推荐方案及理由；技术事实由 Agent 自行调查。
3. **比较有意义的替代方案。** 对有实质权衡的选择，比较当前方案与至少一个较简单的替代：能否不做、少做、合并、按变化做、提前做、共享结果，最后才是并行或扩容。选择减少主要成本且满足业务语义的最小改动。没有真实需求时保留简单实现，不强加 Redis、消息队列、微服务或前端重构。
4. **检验反例。** 选择最可能推翻方案的情形：冷缓存、下游变慢、热点、数据增长、写入与读取竞争等。明确首先失效的位置及保护策略；若风险仍不可接受，回到设计而非叠加补丁。

需要演示推导方式时读 [端到端示例](references/worked-example.md)；需要解释方法来源时读 [方法与适用边界](references/methods.md)。仅加载本次需要的材料。

## 实现和交付

用户要求实现时，完成相关设计后继续编码和验证；设计任务则止于用户要求的交付范围。复用现有数据访问、缓存、交易和可观测组件；先读其契约再修改。让接口表达必要的版本、错误和时效语义，让组件内部承担连接复用、资源边界和清理责任。

实现前选出能区分旧问题与新行为的验证方式，读取 [证据与回归](../engineering-verification/SKILL.md)。迁移、发布和生产测试沿用用户授权，不由技能扩展权限；不擅自改变分支策略或调用其他 Agent。平台细节按项目实际使用相应官方文档/技能，本包不依赖固定供应商。

交付重点是：**触发场景 → 成本或错误如何产生 → 改动消除了什么 → 业务与资源代价 → 证据和未验证项**。保留已知事实、估算、假设的区分。

复用项目现有设计记录和一个 AGENTS.md 入口；只把难以从代码看出的重要取舍写入设计记录，不自动制造成套文档。把复发问题转换为行为测试或公共组件约束。
