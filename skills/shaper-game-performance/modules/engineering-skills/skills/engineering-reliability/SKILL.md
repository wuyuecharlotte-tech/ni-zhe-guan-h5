# 一致性、过载与恢复设计

先明确受影响操作的业务不变量、权威数据源、成功的定义和持久性要求。对展示数据约定允许陈旧时间；对写入约定原子范围、幂等范围及结果未知时的处理。不能用更快或更多 HTTP 200 代替正确性。

## 用时间线检查并发

从当前实现挑选相关时间线，检查每一步的状态与可见结果：

- 旧读开始 → 写入成功 → 旧读晚到。
- 相同操作同时到达，或超时但提交已经完成后重试。
- 用户/租户/视图切换 → 上一身份响应返回。
- 所有实例缓存同时过期，或失败刷新一直占用在途状态。
- 异步消费者处理成功 → 确认失败 → 同一消息再次投递。

从不变量推导事务、唯一约束、条件更新、版本、幂等键或在途合并的选择；只在需要时使用。查询后再写入的应用校验不能替代数据库内原子约束。展示副作用可以合并不代表交易也可丢弃。幂等键的作用域、保留期、参数冲突和结果查询须匹配业务。

## 设计缓存契约

需要明确 key 的身份/权限/参数/版本范围、值的最大陈旧程度、容量、失效和回源规则。遵循当前业务约定，不把“个人数据一概不缓存”或“公共数据一概可共享”作为通用规则。

将未加载、有效、允许陈旧、失效和失败区分开；前端按对应状态展示，不能把未知数据解释成零余额或已完成操作。写后可见性及旧响应处理要跨前后端一致；仅加 TTL 或客户端随机参数不自动提供一致性。

进程缓存和 single-flight 仅在其实例内生效。评估实例扩张、冷缓存和共享缓存故障的回源量；需要协调或共享结果时权衡其维护与可用性成本。条目数/字节、等待者、在途表均设置与业务相符的边界、清理路径和饱和行为。陈旧结果再缓存时保留源版本/时间，避免反复续期。

## 给每类工作明确压力行为

按用户价值与正确性要求区分关键写、关键读、公共展示和附带工作。决定接入、同时执行、排队、等待期限、取消和拒绝行为；给下游与恢复留出余量。以总实例数及其他任务核对总预算。

超时纳入端到端期限；客户端放弃后下游可能仍在执行，传播取消能力与提交状态需分别确认。只对适合的操作做有界退避重试，限制总尝试和总期限，避免前端、函数、SDK层层叠加重试。

异步处理要定义何时才算接受成功、消息持久性、重复投递、顺序、过期和补偿；不可把函数返回后的悬空 Promise 当成可靠后台任务。允许丢弃的埋点与必须完成的账本写入分别设计。

## 推演恢复

选本次最相关的负载/故障：热点、下游变慢、缓存不可用、进程重启或后台积压。说明如何阻止故障传播、用户会看到什么、依赖恢复时怎样避免集中重试或回源。对无法保证的操作明确结果查询/人工处理路径，而非伪装成功。

记录真正改变方案的取舍，保持小任务小设计。实施时复用现有公共组件，调用 [证据与回归](../engineering-verification/SKILL.md)验证相应时间线与资源边界；平台迁移和真实账本操作仍受用户任务范围约束。
