# 前后端性能优化

从用户的一次操作开始，找到耗时和工作量发生的位置，改动主要瓶颈，再验证用户结果。后端工程和游戏前端各自负责专项方法；本入口负责选路、连接证据与判断整体结果。

## 0. 触发时机

- **用户主动请求**：性能/体验优化、性能审计或具体性能症状，进入第 1 节确认范围。
- **编写代码后的主动检查**：完成一个可运行的功能、完成较大代码修改、或用户让你检查刚写完的代码时，在交付前主动应用本技能一次；不以用户说出“优化”为前提。在现有开发流程的构建/功能验证之后执行，沿用已知需求和环境。

主动检查尽可能盘点本次改动涉及的前端、后端和跨层体验维度，检查调用方/下游以及相关回归风险，优先复用已有基线、测试和性能数据。对于有证据、属于当前任务范围且可回退的问题，必须实施优化、交付修改后的代码并复测（交付要求见第 4 节）；无问题时简要报告检查范围与结论，不为证明调用了技能而制造改动。纯文案、注释或不影响运行时的变更只做相称的轻量检查。

主动触发不等于默认获准全项目重构、改数据库或部署云端。若需要扩展到本次改动之外的全面优化，先按第 1 节询问范围；本次会话已经确认全面优化的直接沿用。每个有意义的交付阶段触发一次，只有新改动、失败或未解决风险才追加检查，不因检查自身产生的小修改无限重复全套流程。结束时说明已检查、已优化及未验证项。

## 1. 定义这次任务

### 先确认优化范围

用户提出优化请求但未明确范围时，开始全面优化前先问一次：**“这次希望针对某个具体问题优化，还是全面检查并优化用户体验与性能？”** 推荐全面优化；具体问题可作为优先排查线索，不能仅因用户提到卡顿就自行缩成单点任务。等待答复期间可做项目识别、只读环境发现与基线准备。

- 用户已明确选择“全面优化”，或在本次会话中已确认范围：直接沿用，不重复询问。
- 用户选择“特定问题”或明确限定范围：聚焦该问题及其依赖、回归风险，不扩展成全项目改造。
- 用户选择“全面优化”或明确让你自行决定：尽可能覆盖项目实际适用的前端、后端与跨层体验维度；先盘点覆盖面，再按证据和收益排序实施。修复第一个瓶颈后继续检查剩余维度，不能把单点改善当作全面完成。
- 尚未获得范围答复：可继续独立的只读检查；不把未回复当成同意全面改动。

全面优化不是逐项盲改。前端按下述覆盖盘点执行；存在服务端时，还需盘点请求放大、处理/查询耗时、载荷与序列化、并发/排队、缓存/重试、状态一致性及异常恢复。每项标记证据、结论、是否实施和验证状态；无收益依据的不改，受设备、权限或运行条件限制的写明未测与下一步。交付时区分已验证改善、仅静态检查和未覆盖项，明确实际覆盖范围。

从请求、项目和现有证据确认：**哪项操作、什么设备/负载、何时算正确完成、要求审计还是实施**。已有目标沿用；未知项先标假设，不为填表反复询问。发现错账、重复结算或状态错误时，同时建立正确性问题，不能只追求速度。

先确定执行上下文：本地项目，或 Shaper 已上传页面；活动 API，或多人 Room，或离线游戏。涉及平台能力时按[总包适配](references/host-integration.md)选择现有入口。本技能不创建另一套云服务或交付流程；处于 runbook 阶段时遵循当前阶段的执行边界。

### 平台资源发现门槛

当项目代码、配置、用户说明或用户提供的 EnvId 表明其使用 CloudBase/云函数时，优化前必须完成一次只读环境发现，不能因本地目录没有服务端源码就跳过。用户已提供 EnvId 时直接用它精确查询并与项目配置/API 域名交叉核对；未提供时先查 `auth(status)`，从项目配置/API 域名发现 EnvId 并核对，确认后绑定该环境；再查询环境详情、函数列表、相关函数详情/代码下载信息及可用指标或日志。用户明确要求优化后端/服务代码时，即使当前目录看起来只有前端，也必须先检查项目配置、服务调用点和平台凭据/环境线索，再判断是否触发 CloudBase 发现；不得仅因没找到服务端源码而跳过。账号下存在多个环境时不得猜选；优先用项目中的 EnvId 精确匹配，无法确认才询问用户。离线项目或确认没有平台依赖的任务不触发此流程。

若用户要求“先给代码/先审阅”，云端操作限定只读：下载/读取当前函数代码到工作区副本，保留环境 ID、函数名、代码哈希、配置与采样时间作为基线；优化须保存完整候选源码和本地验证结果，差异补丁仅辅助审阅。除非用户另行明确要求部署，不调用任何云端写入、发布或流量切换操作。

### 服务端代码排查门槛

全面优化中存在服务端，或用户要求后端优化/审阅时，完成环境发现后立即进入源码排查；在前端改完之前就安排这一分支。按[工作量与瓶颈分析](modules/engineering-skills/skills/engineering-workload/SKILL.md)执行：

1. 列出实际接口/任务及调用方，按用户等待、调用频率和数据规模选择关键路径；从用户操作追到路由、服务、数据库/外部请求和后台任务。未取得 SQL/下游实现时，把对应部分标为未检查，不以 RPC 名称推断执行成本。
2. 对关键路径检查请求/查询扇出、重复扫描/计算、同步解析/压缩、并发准入/排队、缓存容量与过期回源、重试、写入后的附加工作；指出成本随并发数、数据量、缓存键数或其他实际变量如何增长。
3. 源码可得时，对优先风险做最小可复现验证：使用实际代码，以受控依赖替身统计调用次数、暂停依赖检查等待关系，或用代表性输入测 CPU/内存。明确替身边界与输入规模；本地机制证据不等于线上延迟或容量。缺生产流量/压测授权时仍完成这些不依赖生产的检查；用户明确要求仅静态审阅时只列代码证据和待验证实验。
4. 每条关键路径留下记录：`操作/接口 → 源码版本与位置 → 下游与增长变量 → 证据/实验结果 → 结论置信度 → 处理状态 → 未测项`。只取得函数清单、下载过代码或看到少量快速日志时，服务端排查仍未完成。只读代码审阅可以使用不访问真实服务的本地诊断脚本，不据此修改产品行为。

交付前检查每条路径记录：尚未检查或仅静态检查的照实标记；有本地机制证据的再按任务范围实施或交付审阅结果。少量成功请求不代表高并发、冷缓存或大存档没有瓶颈。前端验证受阻时，这一服务端分支继续执行。

## 2. 选择第一个观察点

### 前端、后端与跨层入口

- **后端性能优化入口**：[后端工程模块](modules/engineering-skills/SKILL.md)。处理接口/SQL 慢、重复查询、请求扇出、序列化/压缩、冷启动、并发/排队、缓存、后台任务与恢复；明确要求后端优化或全面优化中存在后端时，读取此入口，再按问题进入下列专项。
- **游戏前端性能优化入口**：[Web 游戏前端](modules/web-game-performance/SKILL.md)。处理加载、掉帧、主线程、内存、资源、交互和设备兼容。
- **跨层定位入口**：[跨层证据](references/cross-layer.md)。处理瓶颈未知或接口耗时与用户等待不一致的情况，关联同一次操作的前后端证据。

**后端执行路径**：已有性能问题先读[工作量与瓶颈分析](modules/engineering-skills/skills/engineering-workload/SKILL.md)；涉及缓存、并发、异步、重试或写后刷新时补读[可靠性与恢复](modules/engineering-skills/skills/engineering-reliability/SKILL.md)；尚未实现或需要架构取舍时读[工程设计](modules/engineering-skills/skills/engineering-design/SKILL.md)；实施后的前后对照、正确性和容量边界按[工程验证](modules/engineering-skills/skills/engineering-verification/SKILL.md)验收。CloudBase 项目先完成第 1 节的只读环境发现，不能用本地无后端源码代替云端检查。

按已确认范围读取命中的专项，后续参考由该入口按需选择。特定问题不默认展开两端；全面优化则盘点所有实际适用维度，再按证据决定改动。领域手册列出的启动、稳态、切关、长期运行等是场景候选，不要求无关场景一律实测。

| 当前症状 | 首先读取 | 何时延伸到另一端 |
|---|---|---|
| API/SQL 慢、请求多、回源或排队放大 | [后端性能优化入口](modules/engineering-skills/SKILL.md) | 服务处理与用户等待不匹配，或客户端触发改变了到达率 |
| 掉帧、首次技能卡顿、内存增长、资源加载慢 | [游戏前端](modules/web-game-performance/SKILL.md) | 请求/推送到达、资源等待或重连与卡顿关联 |
| 点击后久等、启动慢、联机延迟，瓶颈未知 | [跨层证据](references/cross-layer.md) | 先采一条完整动作，再进入出现主要等待的专项；不同时猜两端 |
| 尚未实现，需评估负载与方案 | [后端工程入口](modules/engineering-skills/SKILL.md)，由它选择工程设计专项 | 方案改变响应体、刷新频率、客户端资源或状态应用方式 |

用户要求“优化整个前端/全面优化”时，前端专项必须做维度覆盖盘点，不等同于逐项盲目改代码。对启动与首局可玩、资源加载/缓存、渲染与帧尾、CPU/主线程、分配与内存、输入/UI、网络与请求触发、兼容/可访问性、长时运行/异常恢复，逐项标记“适用且检查/不适用及原因/未检查及阻断”。每个适用项都要有证据、问题或无问题结论及验证状态；优先实施有基线支持的瓶颈。聚焦任务只覆盖受影响维度并明确范围，不能称为全量覆盖。

缓存、重试、写后刷新、异步或结算改动补读[可靠性](modules/engineering-skills/skills/engineering-reliability/SKILL.md)；后端实现验收读[工程验证](modules/engineering-skills/skills/engineering-verification/SKILL.md)。离线游戏不要求云环境；Room 不保存战绩仍有实时服务，不自动引入 PG 或 activity_api。

## 3. 用一份证据贯穿定位与改动

- **复现并留基线**：确认操作真的生效，记录版本、环境、负载、结果与原始证据。实际运行方式由平台适配和领域工具共同确定。本地预览/浏览器启动失败或登录受阻时，必须按[预览受阻时的验证路径](references/host-integration.md#预览受阻时的验证路径)核查并尝试适用的 shaper-debug 路径，再界定页面验证阻断。只要求静态审计时不启动运行；要求优化且可运行时完成实测闭环。
- **先发现项目真实边界**：存在 CloudBase 时，完成 EnvId 匹配、环境绑定、函数清单和相关函数代码/配置读取；以云端当前代码哈希区分线上版本与本地静态副本。只有函数名或资源指标不能证明代码已读取；没有可下载源码或授权时记录阻断，不声称完成后端优化。
- **提出可区分的原因**：把现象对应到一个阶段或放大关系，选能否定它的最小观察/实验。未找到原因时继续定位，避免先扩容、加缓存或降画质。
- **跨端时接续证据**：带上同一场景、动作/请求关联、当前版本、已证实阶段和剩余疑点进入另一模块；不重新建立一套无关联基线。关联规则见[跨层证据](references/cross-layer.md)。
- **实施并验证代价**：只改当前有依据的机制，说明成本移到哪里、哪些业务/玩法语义可能受影响。单端足够解决时不强行改另一端。
- **同条件复测**：使用同场景和可比负载，保留失败、超时及波动；检查目标指标与受影响的正确性、画质和资源边界。无收益或不可接受回归时只回退自己的改动，保留结论。

复用项目已有记录；需要新建记录时使用[性能问题记录](templates/performance-case.md)，每个问题一份，单端任务省略不相关字段。不要为同一问题生成互不关联的前端、后端和联合三份报告。

## 4. 给出与证据相称的结果

### 发现性能问题后的代码交付要求

除用户明确限定为只审计、只诊断或只给建议外，优化任务及代码完成后的主动检查中，发现有证据支持、属于已确认范围的性能问题时，**必须实施优化并产出修改后的代码**。不能用问题清单、优化建议、伪代码、云端资源检查或性能报告代替实际代码交付。全面优化中，前端和后端已发现的问题均按此要求处理，不能仅交付前端改动就声称两端优化完成。

沿用会话中已确认的实施范围：优化过程中用户追问“后端有优化吗”“看看代码有没有优化点”，应继续查明、修改并验证，不自动降级成只给建议。用户明确改为“只审阅/只诊断/先不要改代码”时，才遵循该限制；“先不要部署”只限制部署，不限制本地代码修改和验证。

### 主动修改、交付代码，再确认部署

发现范围内且有证据支持的问题后，按以下闭环完成，不把“是否需要我修改”作为收尾问题：

1. **主动修改**：保护用户已有改动，在本地项目或工作区副本实施前后端优化；无需再次询问是否修复已授权范围内的问题。缺少部署授权时继续生成候选代码，真实受阻的逐项记录并完成其他可做部分。
2. **先完成验证**：执行与改动相关的功能、正确性和同条件性能对照，核对副作用、成本与回退方式。保留失败和未测项；未能验证的照实标注，不将未通过的候选当作可部署结果。
3. **交付具体版本**：提供可运行的完整源码目录或代码包、基线版本/哈希、修改清单、验证结果、风险、未解决项与回退方式。补丁可辅助审阅，不能替代完整候选。涉及云端的明确标记“本地候选，未部署”，不以报告或建议代替代码。
4. **交付后请用户确认**：在用户能审阅上述产物后，请其确认这一版候选代码与验证结果；部署前另须明确其是否同意将该具体代码包/版本部署到指定环境/函数及范围。用户已说“先不要部署”时，只请求审阅候选并保持未部署，等待其后续明确部署指令。尚未得到明确部署同意时，不执行上传发布、云函数更新、数据库迁移或流量切换。用户仅确认代码、继续本地验证或认可优化方向，不等于同意部署。已有明确授权确实覆盖同一候选及部署范围时沿用，不重复确认；用户最新要求“先不要部署/等确认”的，以该要求为准。

用户确认前，已授权的实现、验证和打包都应先完成。需要部署后才能取得的线上证据列为待验证，不为补齐证据自行部署。

### 代码与验证产物

- **可用代码**：在项目中保存实际修改后的源码，交付时提供准确文件位置和变更说明；需要独立交付时提供可运行的源码目录或完整代码包。差异文件可辅助审阅，不能以无法应用的片段代替候选代码。必要的依赖声明、配置示例、启动/构建说明随代码提供，排除凭据和用户私有数据。
- **云端候选也要交付**：涉及云函数或后端服务时，在工作区基于已核对版本生成对应函数/服务的优化代码，注明基线版本或哈希、修改文件及运行方式。未获部署授权不阻止本地候选实现与验证；明确标记“本地候选，未部署”，不得把云端检查写成已完成云端优化。
- **报告对应实际代码**：每个已发现的问题记录证据、处理状态、修改文件/代码包位置、前后对照与正确性验证结果，以及未测项。报告中的“已优化”必须能找到对应改动；交付前核对引用文件和压缩包确实存在且包含最终代码。
- **验证决定结论**：运行与改动相关的功能回归和同条件性能对照，记录代价与回退方式。只能本地验证时，明确结论适用范围；未经验证的候选不能称为已验证改善。无收益或产生不可接受回归的改动应回退并继续定位，不能为了交付而保留有害改动。
- **真实阻断要明示**：源码不可得、缺少必要权限/环境、问题超出用户限定范围或尚无可靠修复方案时，完成不受阻的部分，逐项说明阻断、缺失条件及下一步，标记“未完成/待验证”；不能静默改为建议交付，也不能声称相关优化已完成。用户明确只要求审计时沿用该范围；未发现问题时不制造代码改动。

| 结论 | 使用条件 |
|---|---|
| 已验证改善 | 同条件目标指标改善可信，相关正确性/画质/资源验证通过；仅声明实际覆盖的设备和场景 |
| 局部收益 | 某端耗时或资源收益已证实，但用户结果未改善或尚未覆盖 |
| 无确定收益 | 差异在波动内、条件不可比或关键因果证据缺失；说明下一项最小验证 |
| 存在回归/正确性未通过 | 体验或语义出现不可接受问题；区分本次引入、原有与尚未归因，不自动回滚无关改动 |

只做审计时交付已证实风险、假设与验证顺序，不使用“已验证改善”。完成时说明主要原因、改动、基线→候选、代价和未测项；性能结论不替代总包的发布判定。达到约定目标、继续优化收益不足或关键条件确实缺失时收尾，不无限试验。
