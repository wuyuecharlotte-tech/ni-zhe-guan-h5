# 跨层证据与验收

只在跨端或瓶颈未明时读取。本页定义两端交换的证据；工作量模型、渲染诊断和平台操作仍由各自模块维护。

## CloudBase 环境与函数的只读发现

项目代码、配置、域名或用户说明显示使用 CloudBase 时，先按根入口的“平台资源发现门槛”验证目标环境，再分析后端。至少保留以下证据；只记录实际查到的内容，不把资源存在等同于已完成代码审查：

| 证据 | 记录内容 | 能证明什么 / 不能证明什么 |
|---|---|---|
| 环境匹配 | 项目配置中的 EnvId 来源、API 域名/配置交叉核对结果、绑定的 EnvId、查询时间 | 目标环境为何匹配；不能只凭账号默认环境或相似环境名猜选 |
| 函数清单 | 环境内函数名、运行时/版本、与项目调用点的映射依据 | 环境中有哪些候选函数；函数名相似不证明被当前流程调用 |
| 代码基线 | 下载/读取状态、云端代码包哈希、函数名、版本或更新时间；候选副本与基线的对应关系 | 实际检查了哪份代码；若无代码包/源码，只能报告入口和配置审计，不能称为函数代码优化 |
| 配置基线 | 超时、内存、并发/实例等本次相关配置及读取时间 | 当前配置状态；不能单靠配置推断瓶颈 |
| 运行证据 | 指标名称、时间窗、筛选条件、聚合范围、样本量；日志/trace 的查询范围与关联键 | 证据覆盖的对象与时间范围；环境级聚合不能归因到单函数，时间窗口重合也不能证明某次请求的因果 |

下载代码时只保存代码包/解包内容及哈希，不保存含凭据的临时签名 URL。指标若只能按环境聚合，明确标注“环境级、不可归因单函数”；继续使用函数日志、trace、调用路径或受控复现补足归因。对不支持或未开放的指标写“不可用/未查询”，不填零。环境发现失败时记录失败步骤和阻断原因；可继续做本地前端或静态分析，但不得声称已读取或优化云端服务代码。

用户要求先审阅候选代码时，云端动作保持只读。将实际下载的函数代码复制到本地候选目录，记录源函数与基线哈希；修改仅发生在候选副本，提供差异及本地验证。没有用户后续明确部署要求时，不上传、发布、切流或改云端配置。

## 用一个用户结果对齐两端

先定义一次动作的起点和正确终点。例如“点击结算 → 权威奖励只入账一次 → 新余额显示且按钮可继续操作”。“服务提交成功”“前端应用结果”“渲染提交”“屏幕呈现”是不同终点，使用真实可观测的那个并注明限制。

复用已有 trace、profiler 与测试记录，保留四组信息：

| 信息 | 最少需要什么 |
|---|---|
| 场景 | 同一 case/scenario、操作/种子/初始状态、负载、成功判据 |
| 版本和条件 | 前端构建、相关服务实际版本；设备/画质、数据/身份分布、网络、缓存与实例条件 |
| 关联 | 轮次 → 用户动作 → 请求/重试或平台 trace → 两端证据路径 |
| 结果 | 同边界耗时/计数、样本和失败、状态版本/业务断言、已知缺口 |

未知信息标未测或未关联，不编造 ID 或强行补齐整套遥测。单端问题省略无关字段。记录形式复用项目现有文件，必要时使用[问题记录](../templates/performance-case.md)。

## 一次操作的证据如何接续

可观测链：输入 → 请求发出 → 服务排队/处理/下游 → 响应读取完成 → 解析/应用状态 → 提交/可见反馈。事件可能嵌套或并行，按关键路径解释；先标出未测区间，再决定下一步工具。

以结算为例，下面只示意证据关系，不是测量结果或需要新建的日志 API：

```text
baseline-01 / settlement-action-07
  ├─ 页面操作与本地 profiler：点击、发出、读取完成、应用新余额、可操作
  ├─ 现有 traceId：第一次请求；若重试，另记 attempt 及其 traceId
  │    └─ 平台查询结果：业务结果、服务阶段、实际版本与查询范围
  └─ 正确性：同一业务结算键的入账次数、权威版本、显示版本
```

在问题记录里给每个节点写真实证据文件/位置，保留操作与 trace 的实际关联依据。平台日志已有关联标识就复用；浏览器缺阶段时用现有 profiler/User Timing 或允许的临时诊断补充，不假定探针自动采到这些事件。不为填表新增网络请求或伪造平台日志。

- 浏览器局部区间使用同一 performance 时间轴，服务区间使用服务自身时钟。不同机器的绝对时间不能直接相减求单程网络耗时。
- 服务总时间、SQL span 和客户端请求区间可能互相包含，不能累加；各端 P95/P99 也不能相减或相加。
- 只找到同一时间窗口而没有事件关联时，写“相关，因果未确认”；明确缺的是请求关联、阶段耗时还是状态版本。
- 推送/Room 记录消息序号或源版本、收取/应用位置、队列与快照年龄；HTTP 延迟正常不能排除 tick、消息积压或客户端处理延迟。
- ID 用于脱敏证据关联，不作为无界指标标签；日志、缓冲与临时 mark 的开销和生命周期由现有工具管理。

## 从证据决定下一步

| 已有证据 | 下一项区分观察 | 接续到哪里 |
|---|---|---|
| SQL 快但客户端等待长 | 排队/RPC/编码/下载，与读取后解析分开 | [工作量分析](../modules/engineering-skills/skills/engineering-workload/SKILL.md)；读取后才慢则进入前端 |
| 请求到达或推送应用时出现长帧 | 对齐响应批量、parse/apply/upload 与线程时间线 | [游戏前端](../modules/web-game-performance/SKILL.md)；必要时协同减载荷/分批应用 |
| 刷新加快后队列和错误上升 | 每次逻辑动作的总尝试、回源与等待期限 | 工作量分析及[可靠性](../modules/engineering-skills/skills/engineering-reliability/SKILL.md) |
| 联机动作晚到但帧率稳定 | 输入消费、Room tick、消息队列、应用与插值等待 | 平台 Room 能力与前端，平台接入见[适配](host-integration.md) |
| 预热解决首次卡顿但启动/峰值变差 | 冷启动可玩、首次技能、资源峰值及驻留 | 前端内存/资源专项，作为成本转移共同验收 |

进入另一个模块时带上：**场景与版本、证据路径、已证实结论、尚待区分的阶段、必须保持的业务/玩法语义**。新增数据追加到同一记录，不重新采一套无法关联的基线。定位证实只需改单端，就在该端完成。

## 现有工具的实际边界

前端工具位于 `modules/web-game-performance/scripts/`（相对本技能根目录）：

- `backend` 是渲染后端，`buildId` 是前端构建。服务端版本/配置另记；任意新增驱动配置字段不会自动进入正常采样 metadata。
- `browser_probe.js` 采 rAF、显式接入的游戏提交、支持时的 longtask/JS heap 和自定义数值。它不自动产生请求链、动作延迟、GPU 时间或权威业务结果；JS heap 不等于总内存，rAF 不等于实际呈现。
- `analyze_runs.py` 的 comparable 只检查它认识的浏览器字段，不读取平台/服务清单，不证明全链路可比、正确性或容量。按工具原格式分析浏览器数据，再在共享问题记录里引用结果与服务证据。
- Shaper 授权页的采样会话、入口和产物限制见[平台适配](host-integration.md)，不把授权 URL 放进通用驱动。

不改探针格式以塞进服务数据，也不把全部平台日志塞进帧样本。用共同的轮次/动作/证据引用连接原始产物。

## 联合验收的三个维度

1. **用户结果**：同一操作是否更快正确完成；反馈时间、首局可玩或输入结果。缺少用户端证据时只能报告已证实的局部收益。
2. **资源与代价**：主要工作量/帧尾/峰值是否改善；是否转移到启动、后台、设备或更高服务规格。只检验受影响的维度，不要求每次全场景长测。
3. **正确性与质量**：身份隔离、旧响应、幂等、消息语义、玩法和画质等改动相关不变量是否保持。尚未解释的重复发奖使正确性保持未通过；先核对权威记录，不假定候选造成回归。

前后条件改变时说明是否为计划内变量；多项同时改变只能归因到组合效果。保留失败/超时/重试分母、样本量与轮间波动；三轮不自动证明尾延迟或稀有错误可信，几个分位数不能平均成总体 P99。浏览器单用户试验不证明服务容量。实际负载测试按工程模块的模型与已有授权执行。

最终结果使用根入口的结论分类，并保留三个维度各自的证据状态。未测不视为通过；平台发布放行由原流程决定，不由性能分析器代签。
